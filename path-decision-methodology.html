THE DECISION ENGINE

How this model actually decides which path to recommend

Written directly in response to reviewer feedback asking exactly this question. This page describes the actual logic, exactly as it runs today, in full.

How the internal AI decision-making actually works

This is a two-step, rule-based decision. First a pass/fail check, then a simple percentage comparison. Every question counted equally toward that percentage, until this page, and the feature below it, made that adjustable.

The two real steps, in order:

FIRST, WHAT A GATEKEEPER ACTUALLY IS

It gives the team a genuine pass/fail check

Most questions in this model contribute to a percentage, more evidence, higher coverage, gradually. A gatekeeper question works differently: it represents an actual UNESCO requirement that must be satisfied on its own terms, regardless of strength elsewhere. Community consent (FPIC) is the clearest example. A site can have flawless historical documentation, perfect boundary maps, and a beautifully argued case, and still genuinely require more work, because the community was never actually asked. That is exactly what happened during this project: a real conversation with our key contact raised serious, real concerns about proceeding at all, and because community consent is modeled as a gatekeeper, the system correctly reflected that this path needed real, further work, regardless of how complete everything else was. That is the entire reason gatekeepers exist: to keep one missing, non-negotiable requirement fully visible, on its own terms, no matter how strong the rest of the file looks.

STEP 1

Gatekeeper check, a fixed rule, the same for every profile

Every stage has some questions marked as gatekeepers, the ones that reflect an actual UNESCO requirement, community consent, legal protection, and so on, set once for the whole model. If any gatekeeper question for a path is in a critical or major gap, that path's status is set to that failure level immediately, regardless of how complete everything else is. This stays fixed across every profile, by design: a missing legal requirement stays a missing legal requirement no matter how a team weighs the rest.

STEP 2

Coverage percentage, now configurable by "scoring profile"

Among paths with no failed gatekeepers, the model recommends whichever has the highest coverage percentage. Coverage was always calculated as answered questions ÷ total questions, with every question worth exactly the same. That is only true under the default profile. A different profile can give some stages more weight than others, changing which path actually comes out on top, without touching the gatekeeper logic at all.

Can the gatekeepers themselves be changed? The specific set tied to real UNESCO requirements stays fixed, by deliberate design. A site staying labeled "ready" while a genuine, non-negotiable requirement remains unmet would defeat the entire reason this model exists. What a future profile could reasonably allow instead: adding extra questions a specific team wants treated as equally critical, layered on top of the real UNESCO baseline, always keeping that baseline fully intact. Profiles can only add caution, always preserving the fixed baseline underneath, which is the honest line this model tries to hold.

The default profile, live right now

Every stage weighted at 1.0, exactly reproducing the model's original behavior. This is the profile every case study uses unless a different one is explicitly selected.

Why more closed case studies make this genuinely better (… in the system today)

…closed, fully-documented case studies

Each closed case study records its evidence and its real, historical outcome together: which criteria were accepted on first reading, which needed a dialogue round, which turned out to be the actual decisive factor. That is real precedent. The more of these exist in the system, the more informed any future scoring profile can be: a team designing a new weighting scheme can look directly at which stages actually mattered in real, decided cases. Today that comparison happens by a person reading the case studies directly; having the model itself suggest weights from real outcomes is a genuine, further capability worth building toward.

Create a new scoring profile

Give the stages you believe matter most a higher weight, save it under a name, and the model will compute path recommendations differently for anyone who selects it. Nothing here touches the gatekeeper logic, only how coverage is calculated.

Leave a stage on "Standard" if you have no strong opinion about it. Only mark the stages your team genuinely believes matter more, or most, for this profile.
